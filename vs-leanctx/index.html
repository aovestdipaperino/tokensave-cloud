TokenSavevsLeanCTX

LeanCTX is the closest competitor TokenSave has, and the one where its usual arguments land weakest. It is also written in Rust. It also ships as a single binary with no runtime. It is more popular by every public measure. The difference is not implementation — it is scope.

TokenSave v7.12.1 · LeanCTX / lean-ctx v3.10.2 (crates.io, Sep 2026)
The Rust argument does not work here. Everywhere else on this site, "single native binary, no runtime, fast enough to sit in the agent's critical path" is TokenSave's sharpest differentiator. Against LeanCTX it differentiates nothing: cargo install lean-ctx, Apache-2.0, same shape, same no-runtime install story. And on adoption LeanCTX is ahead — roughly 3,800 GitHub stars against 640, and about 17,600 crates.io downloads against 5,400. This page has to be won on scope and depth or not at all.

Where LeanCTX is the better tool

  • It covers the other half of token spend

    TokenSave optimises one thing: the agent reading code. LeanCTX also compresses shell output through 95+ declarative patterns and offers mode-aware file reads — map, signatures, diff, entropy — as a replacement for raw Read. On a real session, Bash results and large-file reads are a large share of the budget, and TokenSave simply does not address them.

  • Hybrid search with embeddings

    Reciprocal rank fusion over lexical and vector recall. TokenSave's search is FTS5 plus graph proximity, with the keywords argument as a manual workaround for conceptual queries. On "where do we handle retries?", where the code says backoff, LeanCTX wins.

  • Persistent knowledge facts

    Free-form remembered facts with categories and keys, exportable. TokenSave's session memory is narrower: design decisions and touched code areas.

  • Portable context packages

    .lctxpkg bundles — SHA-256 stamped knowledge, graph subset and session state — so context moves between machines, teammates and CI. TokenSave has per-branch databases but no portable export.

  • A larger community

    About six times the stars and three times the downloads. On a tool you are betting a workflow on, that is a real consideration.

Where TokenSave is the better tool

  • The graph goes deeper

    Type hierarchies and inheritance depth, cyclomatic and cognitive complexity, Halstead, maintainability index, CRAP, design-structure matrix, Gini inequality, dependency depth, risk-weighted test gaps, a composite health score, dead code, circular dependencies, god-class detection. LeanCTX does graph and impact analysis; it does not do code health.

  • Multi-branch graphs

    Per-branch databases created by copying the nearest ancestor and syncing only the diff, with cross-branch search and diff. LeanCTX has no branch model, and this is the clearest functional gap between them.

  • Deterministic retrieval

    No embedding model means the index is a pure function of your source: index twice, get the same graph, with no model to download, version, or drift. LeanCTX's hybrid search is more capable and less reproducible — a genuine trade, not a win for either side.

  • The agent can edit through it

    Four atomic edit primitives that re-index in place, so the graph stays true after a change.

  • Per-call token metrics

    Every response carries tokensave_metrics: before=N after=M, with an append-only ledger and tokensave gain to price it.

Sustainability

Both projects are free, local and open source, and neither is metered. The difference is scale of contribution: LeanCTX has more people around it.

The fair flip side. No business model also means no funded roadmap, and on paper a bus factor of one. That is genuinely mitigated here, though not in the usual way: the author is proud of not having written a single line of TokenSave by hand. Every line was produced by Claude, working from a specification held and refined by a person who knows how the thing is supposed to behave. What the project depends on is not one person's hand-written code that nobody else can read — it is someone who understands the design well enough to explain it to an agent, and that is a transferable, reproducible skill rather than a private stock of knowledge locked in a single contributor's head. The code is regenerable. The understanding is the asset, and it is written down.

Which should you use

Choose LeanCTX if…

you want one tool covering the whole context surface — code, file reads, shell output — with embedding-backed search, portable context bundles and persistent knowledge facts, backed by the larger community.

Choose TokenSave if…

your bottleneck is specifically structural understanding of code: deep per-symbol metrics, type hierarchies, code-health analytics, branch-aware graphs, and an agent that edits with the graph staying true. The two are close enough that running both is defensible.

Method

Every TokenSave figure on this page was verified against the source at origin/master (v7.12.1), not taken from its own README:

  • 87 tools — asserted by test_tool_definitions_complete in src/mcp/tools/handlers/mod.rs; 86 when the optional ast-grep binary is absent from PATH.
  • 60 languages — counted from the [features] tiers in Cargo.toml: 11 lite, 9 medium, 40 full. The README's "50+" is conservative.
  • 0.24s — wall-clock real time for a complete tokensave status invocation, best of repeated runs on an Apple Silicon Mac. Your hardware and repo size will differ.
  • Zero runtime dependencies — otool -L on the released binary; system frameworks only.
  • LeanCTX figures — crates.io v3.10.2 and download count, the yvgude/lean-ctx repository metadata, and the lean-ctx-bin npm README, September 2026. Tool and pattern counts are from TokenSave's own feature review (docs/LEAN-CTX-COMPARE.md) and were not re-counted against the current release.
