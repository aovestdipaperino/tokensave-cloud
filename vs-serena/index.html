TokenSavevsSerena

Serena is the strongest technical challenge on this site. It reaches semantic understanding through the Language Server Protocol rather than through its own parsers — which means that on the specific question of resolution accuracy, it is right where TokenSave is guessing. It also refactors properly. This is the page where the concessions are largest.

TokenSave v7.12.1 · Serena (oraios/serena), Sep 2026

The honest core of it: LSP beats tree-sitter at resolution

TokenSave resolves cross-file edges with ReferenceResolver, which matches unresolved reference names against known node and qualified names. That is a string-matching heuristic, and TokenSave's own design document is blunt about where it breaks:

"Overloaded names. Three structs named Config in different modules. The resolver picks the one in the same file or the first match, which is often wrong. Method dispatch. validator.check(input) could resolve to any check method. Without type information, the resolver guesses based on proximity. Re-exports and aliases. use crate::auth::User as AuthUser — the resolver tries suffix matching but can still miss. Cross-crate references. Unresolvable from AST alone."

— docs/LSP-INTEGRATION.md, TokenSave's own design doc

A language server has none of these problems, because it has the type information. One textDocument/definition request returns the exact target. Serena is built on that from the start; TokenSave has an LSP pass designed to fix this and it is not shipped — there is currently no LSP code in the MCP server at all. On resolution accuracy, Serena is simply ahead, and will stay ahead until that design doc becomes code.

The trade TokenSave makes in exchange is real, though. A language server must be installed per language, started, and warmed before it answers; on a large project that first request can take many seconds, and the server holds significant memory for as long as it runs. TokenSave's graph is precomputed and on disk, so a query costs a database lookup. Which of those you want depends on whether you value exactness or latency more — and on whether the aggregate questions below matter to you at all.

Where Serena is the better tool

  • It is right where TokenSave guesses

    Covered above and worth repeating: overloads, method dispatch, re-exports and cross-crate references are documented weaknesses of TokenSave's resolver and non-problems for a language server. If your codebase has three things called Config, this difference is not academic.

  • Real refactoring, not a preview

    Cross-file rename, move, inline and safe delete as atomic operations, with the language server guaranteeing every reference is updated. TokenSave's rename_preview shows you what its graph believes would be affected and leaves the editing to you — and its graph is the heuristic one. This is the single biggest capability gap on this page.

  • Live diagnostics

    Serena surfaces the language server's own errors and warnings, so the agent can see it broke something without running a build. TokenSave has no equivalent.

  • Symbol-level editing primitives

    "Replace this symbol's body", "insert after this symbol" — addressed semantically rather than by text anchor. TokenSave has replace_symbol and insert_at_symbol too, but resolved through the heuristic graph rather than a language server.

  • A community fifty times larger

    About 29,500 stars against 640, and active daily. That is a genuine argument on its own.

Where TokenSave is the better tool

  • Questions about the whole codebase at once

    This is the real dividing line. LSP answers questions about a symbol: definition, references, type hierarchy. It has no cheap way to answer "rank every file by churn-weighted complexity", "where is the dependency graph circular", "which symbols are dead", "what is the risk-weighted test gap", or "show me the design-structure matrix". Those need a precomputed graph over the entire project, which is exactly what TokenSave is.

  • No language servers to install, start or feed

    Serena needs a working language server for each language you use — installed, compatible, and warmed up. TokenSave bundles 60 grammars in the binary and needs nothing else. On a polyglot repo, or in CI, or on a machine where the Rust analyzer eats several gigabytes, that difference is the whole ballgame.

  • Latency low enough for the critical path

    A quarter-second round trip with no warm-up is what lets TokenSave sit on a PreToolUse hook that fires on every Agent, Grep and Bash call. You cannot put a cold language server there.

  • Licensing

    TokenSave is MIT. Serena's application is GPL-3.0-or-later and contributions require accepting a CLA. For a tool embedded in a commercial development workflow, that is worth a lawyer's five minutes before adoption rather than after.

  • Multi-branch graphs

    Per-branch databases with cross-branch search and diff. Serena works against your current checkout.

  • Git-aware and porting tools

    Commit context, PR context, diff context, changelog, plus port status and ordering for migration work. None of these are things a language server is positioned to answer.

Honestly: these compose well

Serena for exactness on a symbol and for refactoring it safely. TokenSave for aggregate structure, code health, branch awareness and cheap reflexive lookups. The overlap — find a symbol, list its callers — is the part both do, and there Serena is more accurate while TokenSave is faster and needs no server. Running both is a coherent setup, and if you do, prefer Serena's answer whenever the two disagree about where a reference points.

Which should you use

Choose Serena if…

you want compiler-grade accuracy and real refactoring — atomic cross-file renames and moves, live diagnostics — you work mainly in one or two languages with good language servers, and GPL is acceptable in your setting.

Choose TokenSave if…

you want questions answered about the whole codebase rather than one symbol, you work across many languages or in CI where per-language servers are impractical, you need branch-aware graphs, or you want lookups cheap enough to run on every single tool call.

Method

Every TokenSave figure on this page was verified against the source at origin/master (v7.12.1), not taken from its own README:

  • 87 tools — asserted by test_tool_definitions_complete in src/mcp/tools/handlers/mod.rs; 86 when the optional ast-grep binary is absent from PATH.
  • 60 languages — counted from the [features] tiers in Cargo.toml: 11 lite, 9 medium, 40 full. The README's "50+" is conservative.
  • 0.24s — wall-clock real time for a complete tokensave status invocation, best of repeated runs on an Apple Silicon Mac. Your hardware and repo size will differ.
  • Zero runtime dependencies — otool -L on the released binary; system frameworks only.
  • Serena figures — the oraios/serena repository metadata and README, September 2026. Tool categories and refactoring claims are Serena's own and were not independently benchmarked here.
  • The LSP concession — quoted from TokenSave's own docs/LSP-INTEGRATION.md. That document describes a design, not shipped behaviour: at v7.12.1 there is no LSP code in the MCP server, confirmed by searching src/mcp/.
  • Where this page is wrong or has gone stale, open an issue and it will be corrected.
